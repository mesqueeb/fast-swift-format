# Swift formatter startup

Investigated 2026-10-09 against VS Code Swift 2.16.7 and upstream primary sources. A native formatter extension was subsequently installed and configured in user settings; no system services were added.

## What the measured delay means

Earlier local logs recorded 21.257 seconds for toolchain discovery; reloading recorded 0.572 seconds. A small direct `swift format` invocation took about 0.05 seconds. Follow-up direct `swift-format` invocations with stdin and a repository `--assume-filename` took 13, 10, and 10 milliseconds. These establish a slow discovery interval and cheap formatter invocations; they do not identify which discovery subprocess blocked during the slow run, or establish a guaranteed cold-start formatter cost.

In 2.16.7, `SwiftToolchain.create` finds the Swift executable, resolves its path and manager, reads target/compiler information, locates the SDK, and finds testing support. On macOS that can execute `xcode-select -p`, `xcrun objdump -h`, `xcrun --find swift`, `swift -print-target-info`, and `xcrun --sdk macosx --show-sdk-path`. These are environment probes; the function is not compiling or indexing the project. Setting `swift.path` to the toolchain's binary directory bypasses executable lookup in PATH and makes the compiler probe invoke that executable directly, but still performs manager detection and SDK probes. It is not a demonstrated cure for the 21-second interval. [Versioned discovery implementation](https://github.com/swiftlang/vscode-swift/blob/2.16.7/src/toolchain/toolchain.ts), [setting definition](https://github.com/swiftlang/vscode-swift/blob/2.16.7/package.json).

## Formatting does not need a warm project

The formatter is an independent command-line program. Swift 6 toolchains include it, and `xcrun --find swift-format` locates the executable. Since Swift 5.8 its parser no longer depends on parsing libraries from a particular compiler toolchain. It accepts source through stdin and searches parent directories for `.swift-format`; an explicit configuration overrides that search. An editor integration can invoke the existing executable directly and preserve per-directory configuration, without loading a package or waiting for language services. Newer Swift syntax still requires a sufficiently recent formatter. [Official formatter documentation](https://github.com/swiftlang/swift-format).

Upstream SourceKit-LSP's formatting implementation launches a separate `swift-format` process for each request, sends the current document through stdin, and returns text edits. Keeping SourceKit-LSP alive does not itself keep a formatter process alive. It also finds the nearest `.swift-format` before invoking the formatter. [Formatting implementation](https://github.com/swiftlang/sourcekit-lsp/blob/main/Sources/SwiftLanguageService/DocumentFormatting.swift). This source is upstream main, not a verified match to the particular Xcode binary installed locally.

## Always warm across editors and projects

The stock VS Code extension creates a SourceKit-LSP executable and owns its start/stop lifecycle. Its server-path override selects a program to launch; it does not expose a setting to attach to a shared, already running system service. A global daemon would require custom connection handling or a separate formatter service and editor integration. I found no supported global keep-warm mode in the inspected CLI documentation and extension source. [Versioned language-client implementation](https://github.com/swiftlang/vscode-swift/blob/2.16.7/src/sourcekit-lsp/LanguageClientManager.ts).

Recommendation: use a native VS Code formatting provider configured at user level that calls the existing formatter independently of Swift extension activation, supplies the document path for configuration lookup, and applies edits through the editor. This should preserve normal formatting, undo, and cursor behavior more naturally than a command that modifies the saved file. First verify the integration on a freshly opened editor, on a standalone file, and in projects with different `.swift-format` files. A login job periodically invoking tools might populate caches, but cannot guarantee the OS retains them or avoid VS Code's repeated discovery, and has no demonstrated benefit for this case. Local `swift-format --help` exposes no server or daemon mode.

## Integration options and caveats

`Run on Save` accepts commands in user settings, so it can execute the existing `swift-format` binary across projects. This is a practical experiment rather than a full formatting-provider replacement: commands run only when saving existing files, not when creating a file or using Save As, and formatting writes back to disk after save. [Extension's own documentation](https://github.com/emeraldwalk/vscode-runonsave).

The dedicated `vknabel.vscode-apple-swift-format` extension targets the correct formatter but its repository is archived. Its maintainer announced discontinuation in January 2026. It is a poor default for a durable setup. [Repository](https://github.com/vknabel/vscode-apple-swift-format), [maintainer announcement](https://www.vknabel.com/posts/2026-01-02-discontinuing-of-projects/).

Do not substitute Nick Lockwood's `SwiftFormat` accidentally: it is a different formatter, with different rules and a different configuration format. [That formatter's documentation](https://github.com/nicklockwood/SwiftFormat).

## Remaining diagnosis

Capture timing for each discovery command during a genuinely slow activation. The existing aggregate timer cannot distinguish an Xcode tool lookup, compiler probe, filesystem operation, or process-start delay. A separate upstream report describes slow fresh-checkout activation and suspects dependency resolution, but it remains under investigation and does not prove the cause of this machine's discovery interval. [Upstream issue 2033](https://github.com/swiftlang/vscode-swift/issues/2033).

Per-operation instrumentation on the next reload measured 2,434 ms for discovery, including 1,993 ms in `/usr/bin/swift -print-target-info`, 182 ms for SDK discovery, and 132 ms for toolchain path resolution. Maximum extension-host event-loop delay was 27 ms, so this sample's dominant delay was waiting for the compiler probe rather than a long JavaScript block. It does not establish that the earlier 21-second run had the same cause. The temporary instrumentation remains in the installed Swift extension, with its original bundle preserved alongside it, to capture the next slow activation.

The installed `craftingtablestudio.swift-format-fast` provider invokes the selected Xcode's `swift-format` executable directly. Actual VS Code edits and File → Save operations took 32.7 ms and 14.6 ms in the provider, including process launch. The saved results matched direct CLI output with source-folder line length 100 and nested test-folder line length 200. This verification used standalone files outside the repository. User settings apply the provider across projects unless a project supplies its own Swift-specific override. The configured executable path must be updated if this Xcode installation is removed.

An additional experiment with `xcrun --no-cache` took 3,495 ms to locate Swift and 3,698 ms to locate and invoke its target-info command; the direct compiler invocation took 171 ms outside VS Code. This bypasses lookup caching without clearing caches and supports avoiding the shim, but is not equivalent to rebooting. After setting user-level `swift.path` to the active Xcode toolchain's `usr/bin`, instrumented VS Code discovery took 1,409 ms, of which 1,129 ms was still the direct compiler probe. Startup load and cache state differ between samples, so the reduction cannot all be attributed to the setting. Both absolute paths pin this Xcode installation and should be updated when changing toolchains.

Further diagnosis confirmed that a fresh `TMPDIR` does not isolate xcrun's database: verbose lookup still used the normal user temporary directory's `xcrun_db`. The shell and launchd had no `xcrun_nocache`, `DEVELOPER_DIR`, `SDKROOT`, or `TOOLCHAINS` overrides. The installed xcrun manual warns that bypassing caching often has a significant performance cost. Verbose uncached lookup showed internal SDK metadata queries, and sampled subprocess stacks showed xcrun waiting for these queries while its child `xcodebuild` scanned Xcode plugins through `DVTPlugInManager` and read bundle metadata. This demonstrates one costly lookup mechanism on this machine, rather than relying on the older security-check hypothesis.

The diagnostic replay command `python3 tools/swift-format-vscode/diagnostics/capture-discovery.py --uncached` completed successfully. With profiling overhead, shim detection, toolchain resolution, and the shim compiler probe each took about 3.4 seconds; SDK lookup took 2.5 seconds and the direct compiler probe took 164 ms. Artifact directory: `/var/folders/jk/xkqp97lj59v6_gzp0k47cw180000gn/T/SwiftDiscoveryCapture-iw21na1d`. The forced uncached sequence is not the normal cache-populating sequence and does not prove which operation caused the historical 21 seconds. Unified macOS logs retained no matching process records for that interval. A naturally slow activation trace remains necessary to resolve that final attribution.

## Similar frustrations reported by others

- In December 2024, a user reported waiting 10–20 seconds before build tasks, command plugins, and testing UI became available, asking for a startup below five seconds. The issue is still open in the inspected source. This is a close match to the experience of waiting for extension features, but it does not isolate formatter startup or toolchain discovery. [Slow startup, issue 1250](https://github.com/swiftlang/vscode-swift/issues/1250).
- In January 2026, Alex Hoppen reported nearly a minute of activation on a fresh SourceKit-LSP checkout and suspected package dependency resolution. The report remains under investigation. Dependency resolution is a different stage from this machine's measured toolchain discovery. [Issue 2033](https://github.com/swiftlang/vscode-swift/issues/2033).
- In November 2025, a user reported an initialization regression from 2.0.2 to 2.12.0 in a Bazel BSP project. The reporter traced it to `swift package describe` discovering a parent SwiftPM project, despite SwiftPM integration being disabled. After the resulting fix, the reporter confirmed activation and indexing started within a few seconds. This is a documented resolution of unnecessary project-loading work, rather than evidence that compiler binaries need to remain running. [Report](https://github.com/swiftlang/vscode-swift/issues/1925), [confirmed improvement](https://github.com/swiftlang/vscode-swift/issues/1925#issuecomment-3613209540).
- A separate November 2025 fix removed an awaited debug-configuration dialog that blocked folder activation and SourceKit-LSP until dismissed. That fix predates the installed 2.16.7 version. [Pull request 1914](https://github.com/swiftlang/vscode-swift/pull/1914).

An original 2021 investigation by developer Jeff Johnson offers a more relevant hypothesis for the cold-versus-warm timing shape: the first macOS developer-tool invocation after reboot took over ten seconds, while subsequent invocations were immediate. He traced the shims to rebuilding an `xcrun_db` cache, sampled `syspolicyd` doing code-signing work, and reproduced fast startup after restoring the cache. His tests involved Catalina through Monterey and Xcode 12/13; applicability to the current machine is unverified. This justifies timing the first `xcrun` call and observing `syspolicyd`, not changing security settings or copying old caches. [Original measurements and investigation](https://lapcatsoftware.com/articles/xcrun.html).

## Generic native formatter adapters inspected

`jkillian.custom-local-formatters` registers native document and range formatting providers, pipes the editor text through stdin/stdout, and accepts `${file}` in its command. Its 0.2.0 source guards against unsuccessful processes and unexpectedly empty output. However, it substitutes the raw filename into a shell command, does not handle cancellation, and formats range selections as standalone snippets. Quoting a filename handles ordinary spaces but does not robustly handle all shell characters. [Provider implementation](https://github.com/jkillian/vscode-custom-local-formatters/blob/master/src/extension.ts).

`SteefH.external-formatters` spawns an executable with separate arguments and pipes stdin directly, which avoids that shell interpolation problem. Its own documentation lists variable substitution as unfinished, so there is no configured document filename to pass to `--assume-filename`. Its source resolves output on process `exit` rather than waiting for streams to close. These limitations make it less suitable for reliable formatting across nested configurations. [Documentation](https://github.com/SteefH/vscode-external-formatters), [process implementation](https://github.com/SteefH/vscode-external-formatters/blob/master/src/externalTextFormatter.ts).

`djpai.faster-format-with-cli` offers stdin mode, but documents building a shell heredoc to pipe document contents and excludes files that have never been saved. It does not offer a clear advantage over a small direct-process provider for this requirement. [Extension documentation](https://marketplace.visualstudio.com/items?itemName=djpai.faster-format-with-cli).

For this computer, a small native bridge can avoid these gaps: direct executable and argument-array invocation, stdin from the editor, document filename supplied, process completion/cancellation handling, and editor text edits. The generic adapters demonstrate that this architecture is established; the specific robustness concerns above explain choosing the narrow bridge instead.
